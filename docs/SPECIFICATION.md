# Спецификация

Функциональные требования к `lentovodec`. Этот документ отвечает на вопрос
**«что делает система»**; вопрос «как устроена» — в [ARCHITECTURE](ARCHITECTURE.md),
«как байты лежат на ленте» — в [FORMAT](FORMAT.md).

## 1. Глоссарий

| Термин         | Значение                                                       |
| -------------- | -------------------------------------------------------------- |
| Tape           | Физическая кассета LTO. Идентифицируется UUID и именем.        |
| Session        | Один запуск бекапа, записанный на ленту. На одной ленте несколько, нумеруются с 1. |
| Job            | Конфигурация бекапа: что, откуда, в каком режиме.              |
| Catalog        | SQLite-БД с метаданными всех кассет, сессий и файлов.          |
| TapeLabel      | JSON-ярлык в первом блоке ленты.                               |
| FileMeta       | Метаданные одного файла в конкретной сессии.                   |
| Tombstone      | Запись о **удалённом** файле (`State = Deleted`).              |
| EOD            | End Of Data — позиция после последней сессии на ленте.         |

## 2. Доменные сущности

### 2.1. `Job`

| Поле          | Тип           | Описание                                          |
| ------------- | ------------- | ------------------------------------------------- |
| `Name`        | string        | Уникальное имя задания; ключ в конфиге            |
| `Description` | string        | Человекочитаемое описание                         |
| `Mode`        | `JobMode`     | `"append"` или `"mirror"` (см. 2.2)               |
| `Paths`       | []string      | Список корней для бекапа (файлы или каталоги)     |
| `Exclude`     | []string      | Glob-шаблоны для исключения (см. 2.3)             |
| `SpanDepth`   | int32         | Глубина группировки частей spanning по каталогам (`span_depth`): 0 — резка по файлам (дефолт), N ≥ 1 — группы = каталоги N-го уровня под корнем задания (см. 4.2). Отрицательное значение — ошибка валидации. |

Хранятся в `lentovodec.toml`, секция `[[jobs]]`.

### 2.2. `JobMode`

| Значение   | Сема                                                            |
| ---------- | --------------------------------------------------------------- |
| `append`   | Бекапятся новые и изменённые файлы. Удаления не отслеживаются.  |
| `mirror`   | Бекапятся новые и изменённые файлы **плюс** tombstone'ы на удалённые. Восстановление может реконструировать зеркало каталога на момент сессии. |

> В legacy `mirror` был объявлен, но `Scanner` игнорировал режим. В новом —
> это **первый класс**, поведение строгое и протестированное.

### 2.3. `Exclude` — glob-шаблоны

- Поддержка шаблонов `filepath.Match` (одиночный сегмент) **и**
  `doublestar`-стиля `/**/` для рекурсивных матчей.
- Примеры: `*.tmp`, `.git/**`, `node_modules`, `**/.DS_Store`.
- Матчинг — по полному пути (как в `filepath.Clean`), регистрозависимый.
- В legacy была только подстрока `strings.Contains` — это баг.

### 2.4. `FileMeta`

| Поле       | Тип        | Описание                                                        |
| ---------- | ---------- | --------------------------------------------------------------- |
| `Path`     | string     | Абсолютный или корневой-относительный, всегда `filepath.Clean`  |
| `Size`     | int64      | Размер в байтах (0 для каталогов; для `sym` — длина цели ссылки) |
| `ModTime`  | int64      | Unix-наносекунды (или миллисекунды — зафиксировать в impl.)     |
| `IsDir`    | bool       | true для каталогов                                              |
| `Hash`     | string     | xxhash64 в hex (16 символов); пустой для каталогов и tombstone'ов |
| `State`    | `FileState`| См. 2.5                                                         |
| `Type`     | `FileType` | `reg` (по умолчанию), `sym` или `lnk`                            |
| `Linkname` | string     | цель симлинка или путь первого hardlink; пусто для `reg`         |

### 2.5. `FileState`

| Значение    | Символ в БД | Когда возникает                                            |
| ----------- | ----------- | ---------------------------------------------------------- |
| `Added`     | `'A'`       | Файл есть на ФС, в прошлой сессии (по пути) не встречался   |
| `Modified`  | `'M'`       | Файл есть, изменился Size или ModTime                       |
| `Deleted`   | `'D'`       | Файл был в прошлой сессии, теперь отсутствует (только mirror) |

Правила перехода вычисляются `Scanner.Scan` на основе:
- текущего снимка ФС (через `port.Filesystem`)
- прошлого снимка (через `port.Catalog.GetFilesBySession(lastSessionID)` или
  эквивалентный запрос)

### 2.6. `Session`

| Поле         | Тип           | Описание                                              |
| ------------ | ------------- | ----------------------------------------------------- |
| `ID`         | int64         | PK в таблице `sessions`                               |
| `TapeUUID`   | string        | FK на `tapes.uuid`                                    |
| `Num`        | int32         | Порядковый номер **на этой ленте**, начиная с 1       |
| `Type`       | `SessionType` | `"FULL"` или `"INC"`                                  |
| `Timestamp`  | int64         | Unix-секунды старта сессии                            |
| `JobRunID`   | string        | UUID запуска (для группировки частей одного бекапа)   |
| `Part`       | int32         | Номер части в цепочке spanning-запуска, начиная с 1; обычная (не разделённая) сессия — часть 1 |

`Num` вычисляется как `MAX(session_num) + 1` для текущего `tapeUUID`. Первая
сессия на ленте обязана быть `FULL`. Части одного запуска несут общий
`JobRunID` и лежат на разных кассетах; часть на новой кассете цепочки —
`Num = 1`, `Type = FULL`, `Part = k` (канон раскладки — FORMAT §4.1).

### 2.7. `TapeLabel`

См. [FORMAT §5](FORMAT.md#5-tapelabel-json). Канонические поля: `Magic`,
`FormatVersion`, `Name`, `UUID`, `FormattedAt`.

## 3. Каталог (SQLite)

### 3.1. Схема

```sql
CREATE TABLE tapes (
    uuid        TEXT PRIMARY KEY,
    name        TEXT UNIQUE NOT NULL,
    formatted_at INTEGER NOT NULL
);

CREATE TABLE sessions (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    tape_uuid   TEXT NOT NULL,
    session_num INTEGER NOT NULL,
    type        TEXT NOT NULL CHECK (type IN ('FULL', 'INC')),
    timestamp   INTEGER NOT NULL,
    job_run_id  TEXT NOT NULL,
    part        INTEGER NOT NULL DEFAULT 1,
    FOREIGN KEY (tape_uuid) REFERENCES tapes(uuid),
    UNIQUE (tape_uuid, session_num)
);

CREATE TABLE files (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  INTEGER NOT NULL,
    path        TEXT NOT NULL,
    size        INTEGER NOT NULL,
    mod_time    INTEGER NOT NULL,
    is_dir      BOOLEAN NOT NULL,
    hash        TEXT NOT NULL,
    state       TEXT NOT NULL CHECK (state IN ('A', 'M', 'D')),
    type        TEXT NOT NULL DEFAULT 'reg',
    linkname    TEXT NOT NULL DEFAULT '',
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);

CREATE INDEX idx_files_path    ON files(path);
CREATE INDEX idx_files_session ON files(session_id);
CREATE INDEX idx_sessions_tape ON sessions(tape_uuid, session_num);
```

Отличия от legacy (см. [LEGACY_REFERENCE](LEGACY_REFERENCE.md#что-сломано)):

- Добавлены `CHECK`-ограничения (`type`, `state`).
- Добавлен `UNIQUE (tape_uuid, session_num)` — два одинаковых номера сессии
  на одной ленте невозможно.
- `ON DELETE CASCADE` на `files.session_id` — удаление сессии автоматически
  чистит файлы, явный DELETE не нужен (хотя Catalog может делать его явно в
  транзакции для понятности).
- `part` — номер части spanning-цепочки (§2.6), `DEFAULT 1`: до spanning
  каждая сессия — часть 1. Существующие БД мигрируются автоматически
  (`PRAGMA user_version` 0→1, `ALTER TABLE ... ADD COLUMN`).
- `type` и `linkname` добавлены миграцией схемы v1→v2; старые строки получают
  `reg` и пустую цель.
- `PRAGMA foreign_keys = ON;` и `PRAGMA journal_mode = WAL;` — обязательно.

### 3.2. Контракт `port.Catalog`

| Метод                                    | Назначение                                            |
| ---------------------------------------- | ----------------------------------------------------- |
| `RegisterTape(ctx, uuid, name, ts)`      | Вставка или UPSERT кассеты (при форматировании)       |
| `GetTapeByUUID(ctx, uuid)`               | Получить кассету по UUID (для сверки с ленты)         |
| `CreateSession(ctx, sess)` → `id`        | Создать запись о сессии                               |
| `LastSessionNum(ctx, tapeUUID)` → `int32`| `MAX(session_num)`                                    |
| `SaveFiles(ctx, sessionID, files)`       | Пакетная вставка файлов в одной транзакции            |
| `GetLatestFileStates(ctx, paths)`        | Карта path→FileMeta по последней сессии каждого пути  |
| `ListTapes(ctx)`                         | Все кассеты                                           |
| `ListSessions(ctx, filter)`              | Сессии с фильтром по tape                             |
| `GetSessionChain(ctx, jobRunID)`         | Части запуска по `job_run_id`, упорядоченные по `part` |
| `GetFilesBySession(ctx, sessionID)`      | Все файлы сессии                                      |
| `GetAllFileCopies(ctx, path)`            | Все сессии, где файл встречается (для smart restore)  |
| `SearchFiles(ctx, pattern)`              | Глобальный поиск                                      |
| `DeleteSession(ctx, sessionID)`          | Каскадное удаление                                    |
| `PruneSessions(ctx, before)` → `int64`   | Удаление старых сессий                                |
| `Close()`                                | Закрыть соединение                                    |

`GetLatestFileStates` — пакетный аналог legacy `GetLatestFileState`; один
запрос для всего набора путей сессии (важно для производительности `mirror`).

## 4. Сценарии использования

### 4.1. `FormatTape(name, force)`

1. Прочитать текущий лейбл. Если есть и `!force` → `ErrAlreadyFormatted`.
2. Сгенерировать `UUID` (RFC-4122 v4).
3. Перемотать в начало, записать `TapeLabel`, два `MTWEOF`.
4. `Catalog.RegisterTape(uuid, name, now)`.

### 4.2. `Backup(jobName, opts)`

Сканер сохраняет симлинки и hardlink-пары. FIFO, sockets и device-файлы
пропускаются с предупреждением и учитываются в `Stats.SkippedSpecials`.
Неизменённой запись считается при совпадении размера, mtime,
нормализованного типа (пустой и `'reg'` эквивалентны) и цели ссылки;
владелец hardlink-пары якорит пару, даже если сам не изменился.

См. диаграмму в [ARCHITECTURE §4.1](ARCHITECTURE.md#41-backupusecasebackupctx-jobname-opts).

Опции:
- `Full bool` — полный бекап (не инкремент); по умолчанию `false`.
- `DryRun bool` — только сканирование, без записи на ленту.
- `Verify bool` — верификация после записи (см. ниже); по умолчанию
  `false` (текущее поведение не меняется).

Возвращаемые значения:
- `Session{ID, Num, Type, ...}` — сессия части 1 (на первой кассете
  запуска).
- `Stats{Scanned, Added, Modified, Deleted, Bytes}` — статистика.
- `PlannedParts int` — частей по планировщику `capacity`/`min_tail`
  (§8); 1 — одна кассета. Заполняется и в DryRun.
- `PlannedByBudget bool` — часть 1 спланирована в остаток текущей
  кассеты (дозапись), а не на полную ёмкость.
- `Parts int` — фактически записанные части (ENOSPC-переносы меняют
  кассеты, не число частей).
- `Tapes []string` — имена использованных кассет в порядке записи.
- `Verified bool` — запуск с `Verify` завершился успешно: каждая часть
  перечитана, хеши и состав сошлись; `VerifiedFiles`/`VerifiedBytes` —
  счётчики сверки (сумма по частям).

После скана при заданном `capacity` сессия режется планировщиком
(`domain.PlanSpan`): жадный набор файлов в порядке сканера; файл
больше бюджета — `FileTooLargeError` до записи.

При `job.SpanDepth` ≥ 1 включается резка по границам каталогов
(двухуровневый планировщик; порядок сканера сохраняется —
детерминизм tar'а важнее плотности упаковки):

- **Группа** — записи одного каталога N-го уровня вложенности под
  корнем задания (глубина считается от `job.Paths`, не от `/`:
  задание `/tank/data` при `span_depth = 1` группирует по
  `/tank/data/media`, `/tank/data/docs`, …). Каталог-глава, файлы
  и tombstone'ы поддерева принадлежат группе; сама группа —
  ближайший предок-каталог на глубине N (цепочка короче N
  клэмпится к самому глубокому предку — поддерево целиком одна
  группа).
- файл не влезает в часть и начинает новую группу → граница части
  перед его группой (каталог-глава открывает следующую часть);
- файл не влезает, а его группа уже начата в части → **откат**:
  вся группа переносится в начало следующей части;
- группа целиком больше бюджета → **фолбэк** на файловую резку
  внутри группы (иначе такой каталог перестал бы бекапиться);
  одиночный файл больше бюджета — прежний `FileTooLargeError`;
- каталоги и tombstone'ы бюджет не расходуют, но не рвут группу.

Заполнение кассет в среднем чуть хуже, чем при резке по файлам, —
осознанный обмен на локальность: поддерево целиком на одной кассете,
selective-restore поддерева трогает меньше кассет. Поведение
`min_tail`/ENOSPC не меняется: аварийный перенос части целиком на
следующую кассету остаётся как есть (границы планировщика — про
план, ENOSPC — про физику). DryRun отражает группировку в
`PlannedParts`.

**Spanning (несколько кассет).** Частей >1 или остаток текущей кассеты
меньше `min_tail` — запуск требует смены кассет: use case получает
их через порт `TapeChanger` (CloseTape / RequestNext /
SuggestNextName; интерактивный CLI-промпт в local-режиме, pause/resume
демона — состояние `awaiting_tape`, §6.4). Части пишутся на свои
кассеты: каждая — сессия 1 FULL со своим индексом, `Part = k`, общим
`JobRunID` и обратной ссылкой `continues`; кассета с продолжением
закрывается JSON-блоком-указателем (FORMAT §6.1). `TapeFullError`
посреди части — откат к старому EOD и перенос части целиком
на следующую кассету; два подряд переноса с бюджетом полной ёмкости —
ошибка «уменьшите capacity». Без changer'а запуск с частями >1
завершается `TapeChangerError` до записи.

**Верификация после записи (`opts.Verify`).** LTO ECC ≠ верификация
контента (перезапись соседних дорожек, ошибки серводанных — реальные
истории), поэтому опционально сразу после записи часть перечитывается:
после фиксации в каталоге (`SaveFiles`) и до плановой смены кассеты —
`Rewind + MTFSF(2K−1)` → `ReadSession(dest=nil)`: декодер сверяет
xxhash каждого файла против индекса, use case — счётно состав с
записанным. Верифицируются **только сессии текущего запуска**, не вся
кассета (полная проверка носителя — `ReadTest`); каждая часть
spanning-цепочки — на своей кассете до смены (после eject прочитать
нечем). Прогресс — фаза `verify` (§6.4). Цена — примерно ×2 к времени
записи (то же чтение на той же скорости); дефолт — выключено.
**Политика ошибки:** данные уже на ленте и в каталоге — откат
бессмыслен (перезапись не лечит носитель). Любой сбой верификации —
типизированная `domain.VerifyError{SessionNum, File, Details}`: сессия
в каталоге ОСТАЁТСЯ, запуск завершается ошибкой с текстом «сессия N
записана, но не читается обратно»; решение (ремонт/замена кассеты,
повторный бекап) за оператором.

**Семантика mirror:** при `job.Mode == "mirror"` сканер сравнивает текущий
снимок ФС со снимком последней сессии (любого типа) в каталоге для этого
`Job.Name`. Файлы, отсутствующие на ФС, но присутствующие в каталоге,
получают `State = Deleted` и кладутся в `files` + в индекс на ленте как
tombstone (без tar-вхождения). Это позволяет восстановить зеркало каталога
**на момент любой сессии**.

### 4.3. `RestoreUseCase`

При восстановлении `sym` создаётся симлинк, а `lnk` создаётся операцией
hardlink. Dangling symlink допустим. Пропущенные special-файлы на ленту не
попадают.

Три метода.

#### `RestoreFull(ctx, destDir)`

Аварийное восстановление всей ленты. Перемотка в начало, последовательное
чтение всех сессий; для каждой:
- читать индекс, парсить список `FileMeta`;
- читать tar-поток, для каждого файла проверять xxhash;
- писать в `destDir/path` (или в исходное место, если `destDir == ""`).

На повреждённой сессии: логировать, переходить к следующей через
`MTFSF` до следующего filemark'а.

Кассета с указателем продолжения — часть spanning-цепочки. При
заданном `port.TapeChanger` (Reason=`restore`) восстановление следует
цепочке: закрыть прочитанную кассету → получить следующую → сверить
имя ярлыка с ожидаемым из указателя и обратную ссылку `continues`
индекса первой сессии новой кассеты с UUID предыдущей → продолжить
чтение с её сессии 1. Несовпадение — `ChainMismatchError` сразу,
до восстановления данных (защита от вставленной не той кассеты;
повторный запуск после вставки верной продолжит с пропущенного).
Каталог не обязателен (DR-семантика): цепочка читается с лент,
каталог даёт только best-effort отчёт о длине цепочки. Без changer'а
(например, неинтерактивный запуск) указатель завершает восстановление
предупреждением «вставьте кассету и перезапустите»; файлы прочитанной
части уже восстановлены. Предельный DR — вообще без лентоводца: каждая
кассета цепочки читается голым GNU tar (рецепт `mt`/`dd`/`tar` —
FORMAT §12).

#### `RestoreSelective(ctx, sessionID, paths, destDir)`

Восстановление выбранных файлов из конкретной сессии:
1. Извлечь `session_num` и `tape_uuid` из каталога.
2. Сверить `tape_uuid` с ярлыком установленной ленты: сессия части
   цепочки лежит на кассете своей части — при несовпадении ошибка
   `LabelMismatchError` с именем кассеты, которую нужно вставить.
3. Перемотать ленту в позицию этой сессии: `MTFSF(2*session_num - 1)`.
4. Читать индекс, затем tar, выбирая только нужные пути.
5. Проверять xxhash.

#### `RestoreSmart(ctx, paths, destDir)`

Восстановление «по пути» без знания сессии:
1. Для каждого пути: `Catalog.GetAllFileCopies(path)` — список
   `(sessionID, tapeUUID, sessionNum, timestamp)` упорядоченный по
   убыванию времени.
2. Запросить текущий лейбл ленты; отфильтровать копии, которые на этой
   ленте.
3. Для каждой оставшейся копии: перемотать `MTFSF(2*sessionNum - 1)`,
   попытаться распаковать нужные пути.
4. Если хеш не сошёлся — следующая копия.
5. Если ни одна копия не прочиталась → `ErrNoHealthyCopy`.

> В legacy этот сценарий был самым хрупким из-за отсутствия `MTWEOF` между
> сессиями. В новом формате он детерминирован (см. [FORMAT §9](FORMAT.md#9-правила-перемотки)).

### 4.4. `CatalogUseCase`

- `ListTapes`, `ListSessions(tapeUUID?)`, `GetFiles(sessionID)`.
- `Search(pattern)` — глобальный поиск файлов.
- `DeleteSession(sessionID)` — удаление записи из каталога (данные на ленте
  остаются, но путь к ним теряется).
- `Prune(before)` — удаление всех сессий старше `before`.
- `Rebuild()` — реконструкция каталога из содержимого вставленной кассеты
  (DR: утерян/порчен `lentovodec.db`, кассета, неизвестная каталогу,
  переезд на новую машину). Ярлык → `RegisterTape`, JSON-индексы всех
  сессий подряд (`ReadIndexFiles` + пропуск tar-сегмента `MTFSF(1)`,
  [FORMAT §9](FORMAT.md#9-правила-перемотки)) → `CreateSession` +
  `SaveFiles`; tar-поток не читается — **rebuild ≠ верификация**
  (целостность проверяет `ReadTest`). Идемпотентность: существующая
  сессия (`UNIQUE tape_uuid+session_num`) пропускается — повторный
  запуск безопасен, работает и в живой каталог (дополнит недостающее).
  Кассета с указателем продолжения — Warn «вставьте кассету `<name>` и
  повторите rebuild»: данные прочитанной части уже сохранены, следование
  цепочке без оператора (auto-changer) — бэклог. Отчёт:
  `{TapeName, Sessions, Files, SkippedSessions, NextTapeName}`.

### 4.5. Управление лентой

- `TapeInfo()` — текущий лейбл + (если поддерживается приводом) позиция.
- `Eject()` — `MTOFFL`.
- `ReadTest()` — диагностическое чтение всей ленты с проверкой хешей без
  записи на ФС (для проверки носителя). Возвращает отчёт по каждой
  кассете spanning-цепочки (имя, сессии, файлы, байты); следование
  цепочке и сверка кассет — как у `RestoreFull`; повреждённая сессия,
  в отличие от restore, — ошибка (проверка носителя обязана быть
  честной).

## 6. REST API

Базовый путь `/api`. Формат — JSON. Ошибки — `{"error": "...", "code": "..."}`.

### 6.0. Аутентификация

Все эндпоинты, кроме `GET /api/status` и `POST /api/auth/login`, требуют
аутентификации — один из двух способов (модель двух ключей, как в
Intermasq):

| Способ                  | Заголовок                            | Для кого                     |
| ----------------------- | ------------------------------------ | ---------------------------- |
| Сессия (login/password) | `Authorization: Bearer <session-id>` | Web UI и CLI-команды daemon-режима |
| API-ключ                | `X-API-Key: <api_key из TOML>`       | скрипты, curl, мониторинг    |

- Неаутентифицированный запрос → `401 {"error": "unauthorized", "code": "auth_required"}`.
- Сессионный ID — случайные 256 бит из `crypto/rand`, живёт в памяти демона
  (in-memory map + TTL, без JWT и подписей — один админ, ревокация =
  перезапуск демона). TTL — `session_ttl` из конфига, по умолчанию `72h`.
- API-ключ сравнивается за постоянное время (`crypto/subtle`).
- Header-based аутентификация выбрана вместо cookie сознательно: CSRF
  исчезает как класс (сторонняя страница не может прикрепить кастомный
  заголовок).
- События login (успех/провал, IP, имя пользователя) пишутся в
  аудит-лог (`slog`, поле `event=auth`).

| Метод | Путь              | Описание                                            |
| ----- | ----------------- | --------------------------------------------------- |
| POST  | `/auth/login`     | `{username, password}` → `{token, expires_at}`; rate-limit: 5 попыток / 30 c на IP, свыше — `429` |
| POST  | `/auth/logout`    | удалить сессию (текущую)                           |

| Метод | Путь                          | Описание                                  |
| ----- | ----------------------------- | ----------------------------------------- |
| POST  | `/backup/start?job=&full=&verify=` | запустить бекап, вернуть `taskID` (`verify=true` — верификация после записи) |
| POST  | `/restore/start?paths=&dest=&original=` | запустить restore, вернуть `taskID` |
| GET   | `/tasks/active`               | список активных задач                     |
| GET   | `/tasks/{id}/progress`        | прогресс (текущий файл, %, скорость, лог) |
| POST  | `/tasks/{id}/continue`        | продолжить задачу в `awaiting_tape` (смена кассеты spanning): тело `{"tape_name": "..."}`, пустое — предложенное; 409 не в ожидании, 404 нет задачи; аудит `event=task_continue` |

Прогресс-объект:

```json
{
  "id": "task-abcdef12",
  "state": "running|awaiting_tape|success|error",
  "phase": "scan|write|verify|finalize",
  "current_file": "/path/to/file",
  "processed_bytes": 1234567,
  "total_bytes": 9876543,
  "percent": 12.5,
  "speed_mbps": 145.2,
  "logs": ["...последние 50 строк..."],
  "error": "",
  "message": "",
  "suggested_tape_name": ""
}
```

Расширение spanning: `awaiting_tape` — задача приостановлена, нужна
следующая кассета цепочки (бекап/restore); `message` — текст оператору,
`suggested_tape_name` — предложенное имя (continue с пустым
`tape_name` принимает его). Ожидающая задача остаётся активной
(инвариант «одна активная задача»); graceful shutdown закрывает
ожидание — задача завершается ошибкой отмены, не висит 30 с. Отдельный
cancel-эндпоинт не вводится: отмена ожидающей задачи — остановка
демона.

### 6.7. Файловая система

`GET /api/fs/list?path=/abs` возвращает непосредственное содержимое каталога
ФС сервера: `{path, parent, entries}`. Эндпоинт находится за общей
аутентификацией; он читает ФС от лица демона, поэтому доступ к дереву равен
доступу администратора. В v1 allowlist корней не вводится. Ответ сортирует
каталоги первыми, затем элементы по имени; скрытые элементы не фильтруются.
Несуществующий путь даёт 404 `not_found`, отсутствие прав — 403 `forbidden`,
путь к файлу — 400 `bad_request`.

## 8. Конфигурация

`lentovodec.toml`:

```toml
db    = "lentovodec.db"
device = "/dev/nst0"
log   = "lentovodec.log"
server = "http://127.0.0.1:29201"
log_level = "info"           # debug | info | warn | error

# --- Web-доступ (демон) ---
bind = "127.0.0.1:29201"     # что слушать; 127.0.0.1 — LAN не видит порт
                             # (SSH-туннель см. §9.2); LAN-адрес — осознанный выбор
web_username = "admin"       # учётка ровно одна; пустая строка = auth выключен
                             # (разрешено ТОЛЬКО при bind на loopback)
web_password_hash = "$2a$..." # bcrypt; генерируется `lentovodec passwd`
api_key = ""                 # опциональный ключ для скриптов (X-API-Key);
                             # пустой — отключён
session_ttl = "72h"          # TTL сессий логина

# --- Планировщик частей spanning ---
capacity = "2.2T"            # оценка ёмкости кассеты в байтах (человекочитаемая
                             # строка: суффиксы B/K/M/G/T, степени 1024, дробь
                             # допускается); отсутствие/0 — spanning выключен,
                             # поведение одной кассеты. Рекомендация для LTO-6 —
                             # "2.2T" (с запасом против 2.5T native: сжатие
                             # привода непредсказуемо, оценка консервативная)
min_tail = "100G"            # порог остатка текущей кассеты: остаток меньше —
                             # новая сессия начинается на новой кассете;
                             # дефолт — 5% capacity, но не меньше одного блока

[[jobs]]
Name = "media"
Description = "Бекап сериалов"
Mode = "append"              # append | mirror
Paths = ["/tank/data/media"]
Exclude = ["**/.DS_Store", "**/*.partial"]
span_depth = 1               # резка spanning-частей по каталогам 1-го уровня
                             # под корнем задания (0/отсутствие — по файлам)

[[jobs]]
Name = "system"
Description = "Системные файлы"
Mode = "mirror"
Paths = ["/etc", "/home"]
Exclude = ["/home/*/.cache/**"]
```

Слои применения: defaults → TOML → env (`LENTOVODEC_DEVICE`,
`LENTOVODEC_DB`, ...) → флаги. Секреты (`web_password_hash`, `api_key`)
через env не передаются — только TOML с правами 0600.

`capacity`/`min_tail` включает планировщик частей: после скана сессия
режется на части по границам файлов в порядке сканера (жадный набор в
бюджет), файл больше бюджета кассеты — `FileTooLargeError` до записи
(и в DryRun). Per-job ключ `span_depth` (дефолт 0) переключает резку
на границы каталогов N-го уровня под корнем задания с откатом группы
целиком и фолбэком на файлы внутри негабаритной группы (§4.2). Бюджет
дозаписи — `capacity` минус Σ байт файлов сессий кассеты из каталога
(tombstone'ы не считаются; индексный overhead не учитывается — оценка,
её промах закрывает ENOSPC-перенос §4.2). Разрез сессий по кассетам
(spanning) — §4.2; restore и readtest по цепочке — §4.3, §4.5.

## 9. Нефункциональные требования

| Качество           | Подход                                                            |
| ------------------ | ----------------------------------------------------------------- |
| Логирование        | `log/slog`, структурированно, уровень из конфига                  |
| Отмена операций    | `context.Context` во всех use case; демон глушит задачу по SIGINT |
| Прогресс           | `port.ProgressReporter`, throttle 2 Гц                            |
| Производительность | Блочный I/O 256 KiB; buffering 4 MiB при копировании файлов       |
| Целостность        | xxhash64 каждого файла, проверяется при любом restore             |
| Безопасность       | Rootless: критерий доступа — probe устройства, не uid (см. §9.1)  |
| Аутентификация Web | Логин/пароль (bcrypt) + сессии в памяти; bind по умолчанию loopback (см. §9.2) |
| Graceful shutdown  | Демон ловит SIGINT/SIGTERM, ждёт завершения активной задачи до 30с |
| UID/GID при restore | Опционально, через флаг `--preserve-ownership`; по умолчанию выключено (не требует root) |

### 9.1. Rootless-модель

Управление стримером **не требует root**: `/dev/nst*` — обычное
character-устройство (группа `tape`), ioctl ленты не требуют
`CAP_SYS_RAWIO`. Требует root только `chown` (`--preserve-ownership`) и
доступ к путям ФС, закрытым правами для данного пользователя, — это
ограничения ФС, а не стримера.

- **Критерий доступа** — успешное открытие устройства (probe на старте
  демона и local-команд), а не `uid == 0`. При отказе (EACCES/ENOENT) —
  понятная ошибка с подсказкой (`usermod -aG tape <user>` или
  udev-правило/ACL), а не warning по факту запуска не от root.
- **Рекомендуемое развёртывание** — выделенный пользователь `lentovodec`
  (группа `tape`; `/var/lib/lentovodec` для БД и лога; конфиг только на
  чтение). Демон и все local-команды — от **одного** пользователя: у
  SQLite в WAL-режиме рядом с БД лежат `db-wal`/`db-shm`, смешивание
  пользователей потребовало бы общего group-writable каталога.
- Привилегированный helper (polkit/udisks-style) — рассмотрен и
  **отвергнут**: одна машина, один стример, цена не оправдана.

Инструкция развёртывания (`useradd`, udev, systemd-юнит с харднингом) —
в README (Этап 10). Кодовых изменений модель не требует: доступ к
устройству инкапсулирован в `adapter/linuxtape`, `EACCES` всплывает
наружу естественным образом.

### 9.2. Аутентификация и сетевой доступ демона

Демон — «инструмент одной машины», и по умолчанию он **не виден из сети**:

- **`bind = "127.0.0.1:29201"`** (дефолт). Управление с другой машины —
  через SSH-туннель, аутентификация и шифрование достаются от SSH:

  ```bash
  ssh -L 29201:127.0.0.1:29201 lentovodec@server
  # затем на ноутбуке: http://localhost:29201
  ```

- **Прямой доступ из LAN** — осознанный выбор оператора: меняется `bind`
  (например, `192.168.1.10:29201` или `0.0.0.0:29201`). При этом демон
  **требует** настроенную аутентификацию: не-loopback bind без
  `web_password_hash` (и `web_username`) — отказ старта с понятной
  ошибкой. Порт по умолчанию 29201 (не входит в типовые диапазоны
  сканеров, легко пробрасывается).

Модель аутентификации (референс — Intermasq, упрощено под одного админа):

- **bcrypt** для хэша пароля (`golang.org/x/crypto/bcrypt`; лимит ввода —
  72 байта, bcrypt-ошибки не проглатываются). Хеш генерируется
  `lentovodec passwd` и кладётся в TOML.
- **Сессии** — случайные 256 бит (`crypto/rand`), in-memory map с TTL
  (`session_ttl`, дефолт 72h) и лимитом размера; никаких JWT/подписей —
  ревокация всего и вся = перезапуск демона, для одного админа это
  фича, а не ограничение.
- **Rate-limit** на `/auth/login`: 5 попыток / 30 c на IP (`429` после);
  счётчик сбрасывается при успешном логине.
- **Постоянное время сравнения** для `api_key` (`crypto/subtle`).
- **Аудит-лог**: `login_success` / `login_failure` (IP, username) — в
  общий slog-лог с полем `event=auth`; создание/удаление задач и
  форматирование ленты логируются с именем пользователя сессии.
- HTTP внутри LAN без TLS — принятый компромисс для homelab (токен
  ходит по вашему же кабелю/WPA2); нужен TLS — ставится спереди
  реверс-прокси или используется SSH-туннель, демон ничего не знает
  про сертификаты.

Границы модели (зафиксировано честно): пользователь один, ролей нет;
сессии не переживают перезапуск демона; WebSocket/SSE-эндпоинтов нет
(прогресс — поллинг), так что токен не «утекает» в долгоживущие
соединения.
